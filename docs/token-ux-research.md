# 令牌配置体验调研：多渠道同模型场景与一键式配置

> 调研结论与方案设计（2026-08）。目标：优化「多个渠道提供相同模型」时令牌白名单的配置体验，并为「从零到能调用」提供更快速的一键式路径。
> 本文只做调研与方案，不涉及代码改动。实现优先级与取舍见文末「推荐落地顺序」。

## 1. 现状梳理（代码事实）

### 1.1 数据模型：模型是「渠道 × 模型名」的明细行

- `models` 表（`internal/store/models.go:21`）以 `channel_id + name` 为粒度，**同一对外名可同时由多个渠道各有一行**（如渠道 A/B/C 都提供 `gpt-4o`）。
- 每个模型行有自己的 `enabled`、`alias`（对外别名）、`capabilities`（system/tools/vision/json_mode，可手动覆盖）。
- `tokens` 表（`internal/store/tokens.go:12`）的白名单是**纯字符串数组** `model_whitelist`（存对外名，alias 非空时用 alias），**与渠道无关**；另有 `allow_all` 显式全放行开关（默认关）。

### 1.2 路由：多渠道同模型已被天然支持

- `ListChannelsByModel`（`internal/store/models.go:177`）：按 `name` 或 `alias` 命中、模型启用、渠道 `active`，返回全部可用路由。
- router 层 random/round_robin 选渠道、5xx/网络错误换渠道重试（最多 4 次尝试）、429/401 换 key 冷却 —— 多渠道同模型天然形成负载均衡与故障转移。
- `GET /v1/models` 按当前令牌白名单过滤返回，客户端只看到该令牌可用的模型。

**结论：转发层面已完备，问题全部出在「管理面配置体验」这一环。**

### 1.3 令牌配置现状与痛点

**A. 白名单弹窗信息缺失（多渠道同模型的核心困惑）**

`enabledModelNames`（`internal/web/handlers.go:173`）把启用模型按对外名**去重、排序**后喂给弹窗，每个模型只有一行名字（`tokens.html` 的 `.model-row`），没有任何上下文：

| 缺失信息 | 后果 |
|---|---|
| 该模型由几个渠道提供、其中几个健康（active） | 可能给令牌配上「只由一个已 down 渠道提供」的模型，调用直接 502，用户无从判断 |
| 能力标签（system/tools/vision/json） | 想配「支持工具调用的模型」得先逐个去模型管理页核对，再回来勾选 |
| 按渠道维度查看/筛选 | 模型几十上百时，勾选靠肉眼搜索，没有「该渠道下的模型」视角 |
| 模型分组/常用集 | 每次创建都要重复勾选同一批常用模型 |

**B. 创建流程步骤多，无一键路径**

当前完整链路：打开令牌页 → 填名称 → 「选择模型」→ 弹窗逐项勾选 → 确定 → 「生成」→ 复制令牌 → 复制 curl 示例 → 去客户端手工拼配置。没有任何「从某个模型/某处直接生成令牌」的入口（模型管理页、测试台、渠道页均无）。多令牌批量场景（多客户端/多人）全程重复。

**C. 客户端配置要手工拼接**

生成令牌后只有 curl 示例可一键复制（`tokens.html:67`）。NextChat（网关地址+令牌+模型名）、Claude Code（`ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_MODEL` 三个环境变量）、Cursor（OpenAI-compatible provider）等常用配置都散在「接入指南」文字里，没有「令牌已生成 → 按客户端一键复制配置」的直达路径。

**D. 细节点**

- 测试台下拉（`internal/web/playground.go:64`）**未去重**，多渠道同模型会出现重复选项（顺带发现，非本次重点）。
- 白名单校验语义是「对外名精确匹配」（`auth.CheckModelAllowed`，`internal/auth/middleware.go:33`），多渠道对令牌完全透明 —— 这意味着**白名单数据模型不需要改**，体验问题都在展示层与入口层。

## 2. 方案设计

### 方案 B：白名单弹窗信息透明（解决多渠道困惑，改动集中在 tokens.html + 一个 handler 数据拼装）

每个模型行追加展示：

- **渠道覆盖**：`3 渠道 · 2 健康`（提供该对外名的 active 渠道数 / 总渠道数），0 健康时红色警示「无可用渠道」；
- **能力标签**：复用模型管理页的四项小标签（system/tools/vision/json）；
- **筛选增强**：搜索框旁加「只看有可用渠道」开关 + 能力筛选 checkbox 组；行内快捷按钮「按渠道选」展开该渠道下模型一键勾选。

数据来源：`ListModels` 已返回全量明细，handler 端按对外名分组统计即可，无需新增 SQL。样式与现有 `applySearch` JS 同一模式（服务端渲染 + 原生 JS，不引框架）。

### 方案 A：从模型管理页「一键建令牌」（最小改动、直击「一键式」）

- 模型管理页每行加「建令牌」按钮（也可放测试台），点击后 POST 到现有 `/admin/tokens`（预填 `name` 与白名单=该模型对外名）；
- 复用 `createToken` 现有「POST 后直接 render 令牌页并展示明文一次」的模式（`internal/web/handlers.go:152`），**不能重定向**，否则明文丢失；
- 效果：`选模型 → 点一下 → 复制令牌`，两步替代现在的五步。

### 方案 C：令牌生成后按客户端一键复制配置

`tokens.html` 的「直接可用的 curl 示例」扩展为多条目：

- OpenAI Chat / Anthropic Messages / Responses 三协议各一条 curl；
- NextChat：网关地址 + 令牌 + 模型名三要素组合；
- Claude Code：`export ANTHROPIC_BASE_URL=... && export ANTHROPIC_AUTH_TOKEN=... && export ANTHROPIC_MODEL=...` 一行 shell 片段一键复制；
- Cursor：provider 配置片段。

全部由模板直接拼出、零后端改动（令牌明文只在生成响应里出现一次，模板里已持有）。

### 方案 D（进阶，可选）：令牌模板与批量

- 「常用模型组」一键勾选：全部 / 仅文本 / 仅工具 / 仅视觉（按能力标签）；
- 按用户批量创建（令牌页选归属用户，目前令牌归属于创建者 `user_id`，无此入口）。

### 方案 E（进阶，可选）：测试台验证后转令牌

测试台某模型对话成功 → 「生成可用令牌」按钮，预填该模型 + 名称，直接出令牌与配置 —— 从「验证可用」到「拿到令牌」零跳转。

## 3. 推荐落地顺序与范围控制

1. **方案 B**（弹窗信息透明 + 可用性警示）：一次改动解决「多渠道同模型选错/选到不可用」的最大困惑，无数据模型变更；
2. **方案 A + C**（一键建令牌 + 按客户端一键复制）：满足「快速方便一键式」核心诉求，改动集中在模板层 + 一个 handler 小分支；
3. **方案 D/E**：视使用反馈再做，属于体验增量而非痛点修复。

**明确不做**：白名单按渠道限制（令牌 → 渠道级授权）——与现有「白名单是纯模型名」的设计和 M3 路由语义冲突，属于新需求而非体验优化；如确有需要应单独立项评估。测试台去重可随 B 顺手修掉。

## 4. 约束核对

- 全部方案不引入前端框架/构建工具：弹窗增强沿用现有原生 JS 模式（参考 `tokens.html` 的 `model-search` 过滤）；
- 不改变 `tokens` 表结构、不改白名单校验语义、不动路由与鉴权；
- 一键建令牌必须遵守「明文只显示一次」约束（POST 后同响应渲染，不可 302）；
- 管理面文案保持中文。
